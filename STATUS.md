# Ghost Chat — Полный статус проекта

Дата: 23 марта 2026

## Что это за проект

Ghost Chat — анонимный P2P мессенджер с шифрованием. Три платформы: веб (сайт ghostchat.one), iOS (App Store через TestFlight), Android (APK). Сервер только помогает двум устройствам найти друг друга — после этого всё общение идёт напрямую между устройствами, сервер ничего не видит и не хранит.

## Что НЕ работает (известные проблемы)

### 1. Голосовые звонки — нет звука (КРИТИЧЕСКАЯ ПРОБЛЕМА)

Что происходит: iPhone звонит на веб, веб принимает, но ни одна сторона не слышит другую.

Почему: на iPhone есть специальная система (CallKit) которая управляет микрофоном и динамиком. Она должна "разрешить" приложению использовать аудио. Но она не успевает это сделать, или вообще не делает.

Что было сделано:
- Добавлен код который сам включает аудио через 2 секунды если система не включила
- Проблема: пользователь завершал звонок через 2 секунды, не дождавшись

Что нужно сделать (build 32):
- Аудио включается СРАЗУ при начале звонка, не ждёт систему
- Логи записываются на каждом шаге аудио

Статус: фикс написан, ожидает тестирования на build 32.

### 2. Управляющие сообщения показываются как текст

Что происходит: когда iPhone звонит на веб, на iPhone в чате появляется сырой текст типа `{"type":"renegotiate","sdp":{"type":"answer","sdp":"v=0\r\no=mozilla...`

Почему: каждое сообщение между устройствами — это JSON. Обычные текстовые сообщения и управляющие (звонок, набор текста, подтверждение доставки) отличаются флагом `_ctrl`. Если этот флаг отсутствует — приложение думает что это обычный текст и показывает его в чате.

Проблема: iOS и Android НЕ ставили флаг `_ctrl` на свои управляющие сообщения. Веб ставил. Когда iOS отправлял "начать звонок" → веб получал JSON без `_ctrl` → показывал как текст.

Что сделано: добавлен `_ctrl: true` в функцию отправки управляющих сообщений на iOS и Android.

Статус: фикс написан, ожидает тестирования.

### 5. Push уведомления не приходят

Что происходит: когда один пользователь пишет другому — уведомление не приходит на телефон.

Почему: push работает через Apple (APNs) и Google (FCM). Для этого нужно:
1. Устройство должно зарегистрировать свой push-токен
2. Токен должен быть передан собеседнику
3. Собеседник должен отправить push через наш сервер

На Simulator нет push. На реальном iPhone push-токен генерируется, но обмен токенами между iOS и вебом не тестировался полностью (веб не имеет push-токена вообще).

Между двумя iPhone или iPhone+Android — должно работать, но не тестировалось на двух реальных устройствах.

Статус: код написан, нужно тестирование на двух реальных устройствах.

### 6. Universal Links на iOS (открытие ссылки сразу в приложении)

Что происходит: ссылка ghostchat.one/?room=XXX открывает Safari вместо приложения.

Почему: Apple кэширует файл apple-app-site-association (AASA) до 24 часов. Team ID в файле был исправлен с WDWX83YJFP на правильный G2VZKDYV38, но кэш Apple ещё не обновился.

На Android deep linking работает отлично.

Статус: AASA исправлен на сервере, ждём обновления кэша Apple.

### 7. WebSocket на iPhone обрывается при переключении приложений

Что происходит: когда пользователь копирует ссылку и переключается в Telegram/iMessage чтобы отправить её — iPhone закрывает WebSocket соединение Ghost Chat (приложение уходит в background).

В логах видно: create-room → disconnect через 3 секунды → rejoin → disconnect через 0.1 секунды → rejoin.

Почему: iOS агрессивно убивает фоновые WebSocket соединения.

Как обходится: приложение автоматически переподключается (rejoin). Работает, но создаёт лишнюю нагрузку и задержку.

Статус: работает через rejoin, но можно улучшить.

## Архитектура проекта

### Как устроено подключение (простым языком)

1. Один человек нажимает "Новый чат" → приложение просит сервер создать комнату
2. Сервер создаёт комнату и даёт уникальный код (64 символа)
3. Человек отправляет этот код другому (через Telegram, SMS, лично)
4. Второй человек вводит код → приложение говорит серверу "хочу войти в эту комнату"
5. Сервер говорит первому "к тебе кто-то пришёл"
6. Оба устройства начинают обмениваться данными чтобы найти друг друга напрямую (это называется WebRTC)
7. Когда прямой канал установлен — сервер больше не нужен
8. Оба устройства обмениваются ключами шифрования
9. Теперь можно писать, звонить, отправлять файлы — всё зашифровано, сервер ничего не видит

### Как устроено шифрование

Используется Double Ratchet — тот же протокол что в Signal. Каждое сообщение шифруется НОВЫМ ключом. Даже если кто-то перехватит одно сообщение — остальные останутся защищены.

При первом подключении:
1. Оба устройства генерируют пару ключей (публичный + приватный)
2. Обмениваются публичными ключами
3. Математически вычисляют общий секрет (ECDH)
4. Из общего секрета создают цепочку ключей (Double Ratchet)
5. Каждое сообщение: JSON → дополнение до 256 байт (чтобы нельзя было определить длину) → шифрование AES-256-GCM → отправка

### Как устроены звонки

1. Звонящий отправляет управляющее сообщение "хочу позвонить" через зашифрованный канал
2. Принимающий видит входящий звонок
3. При принятии — оба устройства добавляют аудио-дорожку к существующему P2P каналу
4. Происходит "renegotiation" — обновление параметров соединения чтобы включить аудио
5. Звук идёт напрямую между устройствами, зашифрован DTLS-SRTP

### Как устроены контакты

1. При первом подключении устройства обмениваются "идентификационными ключами"
2. Когда пользователь выходит из чата — приложение предлагает сохранить контакт
3. Контакт сохраняется в зашифрованную базу данных (SQLCipher) на устройстве
4. Сохраняется: имя (которое пользователь придумал), ключ собеседника, push-токен
5. В следующий раз можно нажать на контакт → приложение само создаёт комнату и отправляет push собеседнику

## Ключевые решения и подводные камни

### iOS 26 не показывает NSLog и os_log в syslog
NSLog и os_log с любым уровнем (включая .fault) не видны через pymobiledevice3 syslog на iOS 26 TestFlight builds. Единственный рабочий способ — писать логи В ФАЙЛ на устройстве и потом вытаскивать через `pymobiledevice3 apps pull`.

### xcodegen обязателен после изменения project.yml
Xcode читает .xcodeproj/project.pbxproj, а не project.yml. Если поменять build number или настройки в project.yml и не запустить `xcodegen generate` — Xcode будет использовать старые настройки. Это привело к тому что несколько build'ов были загружены в TestFlight со старым кодом.

### Флаг _ctrl для управляющих сообщений
Все управляющие сообщения (звонки, набор текста, подтверждения, файлы) ДОЛЖНЫ содержать поле `_ctrl: true`. Без него принимающая сторона покажет JSON как обычное текстовое сообщение. Веб всегда добавлял _ctrl, iOS и Android — не добавляли. Исправлено.

### RTCAudioSession на iOS
WebRTC на iOS требует явной активации аудио через RTCAudioSession.sharedInstance().isAudioEnabled = true. CallKit должен вызвать didActivate, но на TestFlight builds и в некоторых edge cases он не вызывается. Решение — включать аудио вручную сразу при начале/принятии звонка.

### WebSocket обрывается при background на iOS
Когда пользователь переключается из Ghost Chat в другое приложение (например чтобы скопировать ссылку) — iOS закрывает WebSocket. Приложение переподключается через rejoin, но это создаёт задержку. На Android такой проблемы нет.

### DataChannel на iOS — порядок delegate
Когда один устройство создаёт комнату (host), а другое заходит (guest) — host создаёт P2P канал (DataChannel). Guest получает этот канал через callback. Если delegate для канала не назначен ВОВРЕМЯ — первые сообщения теряются. На Android это решено назначением delegate прямо на WebRTC потоке. На iOS — добавлен fallback через проверку состояния канала.

### Saved messages выключены по умолчанию
История сообщений НЕ сохраняется по умолчанию — это сделано для максимальной приватности. Пользователь может включить в настройках.

### Контакты не сохраняются для веб-пользователей
Если собеседник — веб (не iOS/Android приложение), контакт не предлагается сохранять. Это потому что веб не имеет push-токена и не сможет получать уведомления о входящих сообщениях.
